{# Two-bar chrome for Jinja pages (UIR-4). Admin's bar one is already React (admin-app). Bar two is rendered here so Jinja admin pages get the *same* chrome as the member SPA without a cross-app import — member-app and admin-app are separate Vite builds and importing across them breaks the build. The shared artifact is the stylesheet, not the markup: `gt-appbar.css` is linked by base.html, base_empty.html and base_admin.html alike, and both renderers emit the same class names. That is what actually governs appearance. `tests/test_chrome_parity.py` asserts the two stay in step, so a class rename in one cannot silently drift from the other. Usage: {% import 'partials/chrome.html' as chrome %} {% call chrome.contextbar( views=[('all', 'Libraries', url_for('library.libraries')), ('scans', 'Scans', url_for('main.scan_management'))], active='all', summary='12 libraries') %} Add library {% endcall %} Views are (id, label, href) triples: in Jinja these are links rather than buttons, because a page swap is a navigation here, not local state. They still render as the same segmented control. #} {% macro contextbar(views=None, active=None, summary=None, label='Views', data_toggle=None, views_id=None) %} {#- `data_toggle` is for pages whose views are panes of the *same* document (Bootstrap tabs). Pass 'tab' and give each view a `#panel` href: the segment still renders as a link — middle-click and copy-link keep working — but the switch stays client-side instead of becoming a full page load. Leave it unset when the views are genuinely separate pages. Two details are load-bearing, both verified against the vendored bootstrap 5.3.2 bundle rather than assumed: * The plugin binds via `closest('.list-group, .nav, [role="tablist"]')` and does nothing at all when that misses — a `role="group"` strip would render perfectly and switch nothing. * `_getActiveElem()` looks for Bootstrap's own `active` class to know which pane to hide. Marking the current segment only with our `is-active` leaves it null, and the first click then shows the new pane without hiding the old one. So in tab mode the container is a tablist and selection is marked with `active` *instead of* `is-active` — the plugin moves `active` on every switch and never touches `is-active`, which would otherwise stay welded to whichever segment happened to render first. `gt-appbar.css` styles both. Outside tab mode nothing changes: these are ordinary links. -#}
